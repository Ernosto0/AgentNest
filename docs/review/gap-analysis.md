# Gap Analysis of the Original Specification

**Purpose:** Record what the planning audit found in the original specification ([`docs/idea.md`](../idea.md)), why each issue matters, and where the revised documentation resolves it.
**Audience:** The founder and any engineer or coding agent who wants to know *why* the revised plan differs from the original.
**Date of audit:** 2026-10-15

---

## 1. Repository assessment (before any changes)

| Item | Finding |
|---|---|
| Files | Only `docs/idea.md` (1,188 lines). No application code, configuration, dependency manifests, CI or tests. |
| Git | Repository initialised on `main`, **no commits yet**. `docs/` untracked. |
| `.claude/` | Present and empty: no project settings, no `CLAUDE.md`. |

**Consequence:** This is a greenfield project. `docs/idea.md` is the only source of intent. It is kept unchanged as the historical input. The revised docs supersede it wherever they conflict, and [requirements.md](../product/requirements.md) traces every requirement back to a section of `idea.md` so that nothing is dropped without a record.

## 2. Overall verdict on the original specification

The original specification is unusually strong on **principles**. It already insists on verified facts, explicit approvals, deterministic workers, honest reporting, simulated-vs-real separation and a small agent surface. Most of these principles are kept.

The weakness is that principles are stated **without the mechanisms that enforce them**. Phrases like "grounded in facts", "retries must not create duplicate posts", "enforce workspace isolation" and "the LLM cannot bypass approvals" name the desired property but not the design. A coding agent working from `idea.md` alone would have to invent the most safety-critical parts of the system. The specification also assumes several Instagram capabilities that are more constrained than it implies.

## 3. Findings

Severity scale:
- **Critical**: would cause incorrect external actions, fabricated business claims, or would block the product's core path.
- **High**: would cause major rework or a serious trust/safety failure.
- **Medium**: produces ambiguity or rework but is containable.
- **Low**: polish or clarity.

An LLM can still type a wrong price. | A single invented price, opening hour or discount sent to a customer is the product's worst failure. ## 4. What the original spec got right (kept as-is)

- Business owner as the authoritative source of business facts.
- Mock adapter behind the same interface as the real adapter.
- Deterministic publishing that does not depend on an LLM session.
- Reports from stored records only.
- "Scheduled ≠ published" honesty.
- Configurable autonomy per action type, defaulting to supervised.
- One codebase for Turkish and global experiences.
- Avoiding multi-agent complexity and a CRM schema in the MVP.
- Pilot validation goals (10–15 business interviews, paid commitments before heavy investment).

## 5. Assumptions that were changed

| Original | Revised | Reason |
|---|---|---|
| Redis + Celery from the start | PostgreSQL job table only | G-08 |
| Eight agent-like components | Four bounded LLM tasks + deterministic services | G-09 |
| Fact versions as previous/new pairs | Full value snapshot per version + separate candidates | G-14 |
| "Flag" scheduled content on fact change | Move to `on_hold`, requires re-approval | G-05 |
| Story copy as caption | Overlay text suggestion; text must be in the image | G-06 |
| Website extraction in onboarding | Pasted-text extraction in MVP; URL fetch deferred | G-30 |
| Telegram as "possible early" channel | Web first; external channel chosen from pilot evidence | G-18 |
| Apache-2.0 as candidate | Undecided; trade-offs documented; decision required before public release | G-22 |
