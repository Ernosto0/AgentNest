## Implementation and contracts

- `agent/control.py` provides owner-only, expected-version controller activation/rollback. `POST /accounts/{id}/agent/activate` accepts `expected_config_version`, a UUID `client_request_id` and `mode=agent|legacy`. It advances account epoch/configuration and a separate cutover generation. Replaying the most recent identical request is idempotent; a changed mode under that request conflicts. Older request versions fail safely rather than reapplying. Existing accounts remain legacy until this explicit action. Activation starts new DM threads on incoming customer messages; it does not send unsolicited replies to historical legacy conversations.
- Signed inbound processing serializes account ownership before conversation routing. One event reaches the selected controller. Paused agent accounts still record ordered inbound work for resume. Legacy preparation, plan persistence and automatic dispatch reject displaced ownership; the dedicated cutover generation also rejects an old legacy plan after an agent-to-legacy round trip, while ordinary inactive-agent policy edits do not alter legacy authority.

Customer date/time questions use the same closed server-rendered question; no global claim-validator exemption was added. Prices and other business claims still require exact fact IDs/versions and placeholders.
- A server-built customer-event response obligation creates one stable action and existing reply draft/send job. Generated wording or tool call IDs do not create another intent. Queued/in-flight/unknown sends reserve the thread slot across new goals and inbound events. Result-only wakes cannot establish a customer send obligation. Automatic mode projects the exact policy grant to the existing executor. Ask mode preserves the original human `agent_action` approval, author and payload hash; it does not invent a human or secondary policy approval. Off mode does not send. Human decisions reserve the configured daily action limit under the account lock, so multiple pending asks cannot bypass a delegation limit.
- The coordinator immediately yields into a server-validated action-backed operation wait after enqueue, even before an operation ID exists. An approval wake arriving before the send remains waiting without another model call. Completion cannot claim a queued/in-flight/unknown DM result is verified. Subsequent model steps receive an observation reconstructed from action/draft/ledger rows. Recovery polls action-backed waits and finds a committed terminal draft/operation even when a worker died between result commit and wake enqueue. Ambiguous sends continue through the existing reconciler and never blindly resend.

Takeover/release increments thread ownership, invalidates pending steps through transition/audit helpers, and prevents the takeover-release ABA race. Native owner echoes take over the thread; app echoes remain non-conversational.
