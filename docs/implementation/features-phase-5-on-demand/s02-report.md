## What was delivered

- **`WhatsAppChannel`** (`backend/app/integrations/channels/whatsapp/adapter.py`) implements `OwnerChannel.deliver_notification` on the existing delivery ledger. Inside the existing `deliver_channel_notification` job it reads the notification, the link and the window anchor in one short transaction, chooses template or session, writes a `send_state = "sending"` marker and **commits**, then makes the single HTTP call with no transaction open, and returns a `DeliveryResult` whose metadata the job now merges into the ledger row.
- **Window rule** (`whatsapp/window.py`, pure): `choose_send_mode(last_inbound_at, now)`. `age < 24h - 5min` is `session`; `age >= 24h - 5min` is `template`; no inbound message ever, or one in the future, is `template`. Decided at **send time** from the injected `Clock` (a message recorded at 23h50 whose worker runs 30 minutes later goes out as a template). The 5-minute margin covers Meta counting the window slightly differently from our webhook timestamp. Both sides of the boundary, the exact boundary, 24h, 24h+1s and the future case are unit-tested, and the two outcomes are also tested end to end through the job queue.
- **Window anchor.** `channel_links.last_inbound_at` (migration `0071`). The Session 01 webhook now sets it for **any** message from a linked owner (text, button tap, image, anything): Meta's own message timestamp when valid and not in the future, otherwise `Clock.now()`; it only moves forward, so a late retried webhook cannot extend the window. A message from an unknown number changes nothing.
- **Template registry** (`whatsapp/templates.py`, the single source): 10 templates x TR and EN, category **utility**, names with a version suffix (`agentnest_approval_requested_v1`, ...). They cover the Web Push types (`approval.requested`, `owner_question.requested`, `owner_question.window_closed`, `content.failed`, `reply.failed`, `account.needs_reauth`, `quota.warning`, `quota.grace`, `quota.paused`) plus the **daily summary** `report.daily_ready` (`agentnest_daily_summary_v1`, four variables: the report date and three counts). Tests enforce Meta's rules (name charset, `_vN` suffix, utility only, sequential positional variables, no variable first or last, length), that variables are numbers or a date only, and that the names appear in the docs table. The same rendered text is sent as a session message inside the window.
- **Dispatch** (`notifications/whatsapp_dispatch.py`, called from `notify` after Web Push): for a type in the new `catalog.WHATSAPP_TYPES` (Web Push types plus `report.daily_ready`), a configured server and a member with an **active WhatsApp link**, it writes a `notification_deliveries` row with the status chosen by the existing quiet-hours policy (`skipped_quiet_hours` for a held message, critical and expiring approvals bypass) and enqueues the existing job, inside the caller's transaction and behind a savepoint that never fails `notify`. An unlinked owner gets nothing recorded. Simulated notifications are never sent.
- **Daily summary numbers.** `reporting.service.generate_daily_report` now adds three integer counts (`inbound_messages`, `replies_sent`, `pending_approvals`) to the `report.daily_ready` params next to `local_date`, so the adapter needs no import of the reporting module (import-linter forbids it). The adapter reads only those keys, accepts only non-negative integers and an ISO date, and refuses to render otherwise (`template_variables_missing`, terminal). No customer text can become a variable.
- **Cost metadata** (`whatsapp/costs.py`) in `notification_deliveries.delivery_metadata.cost`: `send_mode`, `is_template`, `category` (`utility` for a template, `service` for a session message), `template_name`, `template_language`, `pricing_note`, `price_verified: false`, `price_amount: null`, `currency: null`. **No price is recorded:** Session 01 recorded none, and the Meta pricing page read again on 2026-11-18 names Türkiye as a standalone market (utility and authentication rates lowered from 2026-04-01) without an amount or currency; the rate card was not read. The notes also encode the facts that matter for cost: a free tier of 1,000 delivered service messages per number per month, and utility templates charged even inside an open window since 2026-10-01, which is why a session message is preferred whenever the window is open. Meta's later status webhooks store `provider_status` and a `billing` subset (`billable`, `pricing_model`, `category`, `type`; never an amount) on the same row; a `failed` status marks the delivery failed.
- **Failure handling on the ledger's retry/backoff** (job: 3 attempts, 5/30/120 s). 429 and 5xx (the provider answered, nothing accepted) are `retryable`: the row stays `pending` until the last attempt, then `failed` and a dead job. Any other rejection is **terminal** (`whatsapp_rejected:<code>`, only the integer code, never provider text). An **ambiguous** send (transport error or timeout, a 2xx without a message id, any unexpected error after the marker) is failed terminally as `whatsapp_send_ambiguous` and is **never re-sent**, however long the worker waits. If the worker dies between the call and recording the result, the next attempt finds the `sending` marker and fails as `whatsapp_send_state_unknown` instead of sending again. The access token never reaches the ledger or a log line (tested).
- **`WHATSAPP_TEMPLATES_APPROVED`** (default `false`, documented in `.env.example` and `environment-variables.md`): while false, a message outside the window fails with `whatsapp_templates_not_approved` and no template is sent; session messages inside the window are unaffected.
- **Job change** (`notifications/jobs.py`): the job merges the channel result's metadata (minus its own `retryable` and `terminal` flags) into `delivery_metadata` for every channel. Telegram and Web Push only add their small existing metadata (message id, device counts).
- **Docs.** `platform-capabilities.md` new §2.2: the window rule, cost metadata, the **Meta Business Manager template submission steps** (prerequisites, create in WhatsApp Manager or `POST /<waba-id>/message_templates`, category, naming, language, example values, review up to 24 hours, status values, when to set `WHATSAPP_TEMPLATES_APPROVED`) and the table of all 10 templates with the TR and EN bodies, sources and access date 2026-11-18, and what is not verified. ADR-027 got a Session 02 addendum (window rule, opt-in, no simulated data, cost, ambiguity). `integrations.md` (delivery flow), `data-model.md` (the two new columns and the index), `mvp-scope.md` (F-06 row) and `environment-variables.md` updated.

## Deviations and limitations

- **No per-category WhatsApp preference.** Linking the number is the opt-in; every supported type reaches a linked owner (Web Push has an opt-in per category). Recorded in ADR-027; a preference setting is a follow-up if pilot owners find it noisy.
- **Quiet hours hold, they do not release.** A held message is recorded as `skipped_quiet_hours` and is not sent later; this is the existing policy for Telegram and Web Push. A daily summary generated inside quiet hours (a workspace with a late `daily_report_hour`) is therefore not delivered on WhatsApp.
- **Status webhook race.** A status that reaches us before the job has recorded the message id is dedup-marked and not attached (the ledger row has no `wamid` yet). Later statuses for the same message (`delivered`, `read`) are still recorded. Statuses for the fixed link replies have no ledger row and are ignored.
- **Window anchor is a stored time, not Meta's view.** The 5-minute margin and Meta's own timestamp are best effort; a rejected session message fails terminally rather than falling back to a template automatically.
- **5xx is treated as retryable** (Session 01's client classification), 429 certainly so. Only a transport failure or a 2xx without an id counts as ambiguous, so a 5xx that actually delivered the message could duplicate it once; this follows the client contract from Session 01 and was not changed.
- **Template status is a manual switch.** `message_template_status_update` webhooks are not handled; the owner of the account flips `WHATSAPP_TEMPLATES_APPROVED` after checking WhatsApp Manager.
- **No prices.** See above; the cost view is category counts until someone reads Meta's rate card for the sending number's billing currency.
- **No deep links** in the WhatsApp texts ("open the app"). Links in templates need a URL button or variable; left for Session 03 together with buttons.
- **Daily summary counts come from the stored report** at generation time (they can differ from the live app a few hours later).
