## What was delivered

- **Eval sets**: `backend/evals/draft_reply/reply_ru.yaml`, `reply_de.yaml`, `reply_ar.yaml` (dataset names `draft_reply_ru|de|ar`), **20 cases each** (60 in total; at least 12 per set are hard assertions). Per language: prices (monthly, unknown product not guessed, unverified student price never quoted, `do_not_share` policy), hours, address, booking (including an invented time slot that must not appear), out-of-scope (a person answers), complaint, refund, discount, legal (ru and ar; de has complaint/refund/discount), injection (ignore-instructions, system-prompt request, `{{fact:...}}` smuggling, injection on an ordinary question with automation set to `auto`), and language boundaries (language not enabled, mixed German/English, Ukrainian vs Russian, Persian vs Arabic). The Arabic set also covers Arabic-Indic digits in the customer's message, vocalisation marks, and an invented `٦:٣٠` time.
- **Harness changes** (`evals/loader.py`, `evals/runner.py`): a dataset-level `defaults:` block (used for `languages`), a new `language:` expectation (`ru`, `de`, `ar`, or `none` for "a person answers") so a case cannot pass for the wrong reason (for example, a hand-over caused by failed detection instead of by the injection rule), and the automatic-reply notice in the harness now comes from `DEFAULT_DISCLOSURE` per language instead of a fixed Turkish sentence.
- **Fake provider** (`ai/tasks/draft_reply.py`): recognises hours, address, phone, booking, offers, services, greetings and price words in ru/de/ar (Russian `сколько` alone no longer means "how much": "во сколько вы открываетесь?" is an hours question), replies from per-language text, and a wider list of generic German price words so a price question with no product still answers while an unknown product still fails closed.
- **Defects the eval sets found, fixed**:
  - `ai/injection.py`: no ru/de/ar patterns existed, so an injection attempt in those languages raised no `INJECTION_SUSPECTED` signal. Added ignore-previous, previous-instructions, system-prompt, you-are-now, developer-mode and reveal-instructions patterns for ru, de, ar, run on the reply-language fold with invisible marks and Arabic vocalisation removed. The English/Turkish patterns now also run with direction marks and zero-width characters stripped (an `ignore‏ previous instructions` bypass).
  - `inbox/escalation.py`: Arabic particles attached to a word (`بمحامي` "with a lawyer") defeated the keyword match. An optional proclitic group (`و ف ب ل ك`, `ال`, `لل`) now precedes every Arabic keyword.
  - `inbox/language.py`: ordinary short messages in the three languages carried no word from the lists and were handed to a person (fail-closed but wrong). A few dozen common words were added (ru about 36, de about 38, ar about 19, each commented). Words that collide with English (`die`) were rejected by the existing negative tests and removed.
  - `inbox/drafting.py::_label`: owner fact labels exist in Turkish and English; a ru/de/ar reply now prefers the English label and then Turkish (it used Turkish first), matching how formatted values already fall back.
- **Per-language automatic-reply notice**: `DisclosureText` (workspace settings) accepts `ru`, `de`, `ar` next to `tr`, `en`; Session 10 had only the built-in texts. `openapi.json` and `schema.d.ts` patched; the frontend fixture updated.
- **Reply-language setting** (`frontend/src/features/settings/WorkspaceSection.tsx`): the owner's "Edit" form now has a "Customer reply languages" group with Turkish, English, Russian, German and Arabic checkboxes. The workspace's main language is on and cannot be switched off. A coverage line is always shown ("draft quality is tested only for the languages listed here, a message in any other language is always passed to your team"). Choosing Russian, German or Arabic adds an attention notice (these languages are tested with fixed sample conversations, not yet with the owner's customers; read each draft; the account agent answers in Turkish and English only so ru/de/ar conversations are passed to your team). The read-only row repeats the agent note when a new language is on. Only changed fields are sent (`reply_languages` in a stable order, main language first); a server rejection shows next to the list. TR and EN strings added (`settings.workspace.replyLanguages*`).
- **RTL display**: `dir="auto"` on the customer message text, the voice-transcript block (plus a `lang` attribute, and ru/de/ar transcript labels instead of "Another language"), the draft text, the suggestion text, the edit-draft textarea, the manual reply composer, the conversation-list preview and image-description text, in the inbox and in the approval view (which reuses the same components). Only the text elements get the attribute, not the bubbles or the page, so layout, alignment of bubbles and the interface direction are unchanged.

## Deviations and limitations

- **The live run is pending.** The fake provider is deterministic and keyword-based; passing it proves the deterministic layers (language choice, escalation, grounding, validator, policy) and the harness, not the real model's quality. Run `uv run python -m evals run --task draft_reply --provider openai` (needs `OPENAI_API_KEY`) and record accuracy per `draft_reply_ru|de|ar` dataset before any pilot enables a language.
- Eval sets were written by the session lead (an LLM), not by native speakers; the Arabic and Russian phrasing and the three languages' escalation words need a native read.
- Detection is still word-list based: a message in these languages with no listed word goes to a person. The lists were widened from what the eval sets found; real traffic will find more.
- Fact labels, owner-written localized text and the fake's reply text are English/Turkish; ru/de/ar replies render values (numbers, hours, phone) in the reply language but labels fall back to English. The approved-answer screen in the web app still offers only Turkish and English (the API accepts all five).
- The account agent stays Turkish and English only; the settings notice says so.
- The injection patterns are heuristics: a miss still cannot auto-send (approval is required by default and critical values come only from placeholders).
- `dir="auto"` decides by the first strong character: a draft that starts with a Latin word and continues in Arabic displays left to right. Fact chips inside Arabic text follow the bidi algorithm; a rendered value such as `6.000 ₺` next to Arabic words can look reordered. The server already adds directional marks around Arabic hour ranges (Session 10); price chips were not changed.
- Voice-note transcripts still always need approval (R18).
