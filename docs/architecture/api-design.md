# API Design

**Purpose:** HTTP API conventions and endpoint groups, with request and response shapes where they matter for correctness. FastAPI generates the full OpenAPI schema from code. This document defines the contract that the code must satisfy and the phase that introduces each group.

The planned Phase 7.5 account agent, delegation, question, memory and comment routes are specified in [account-agent-contracts.md §5](account-agent-contracts.md). They use all conventions below and are not implemented yet. Sessions 03 and 08–15 add typed routes and regenerate the client as they land.

## 1. Conventions

| Topic | Rule |
|---|---|
| Base path | `/api/v1`. Workspace-scoped resources live under `/api/v1/workspaces/{workspace_id}/…`. Public integration endpoints are under `/webhooks/…` and `/oauth/…` (no `/api/v1` prefix). |
| Format | JSON, UTF-8. Field names in `snake_case`. |
| Auth | Session cookie `agentnest_session` (HttpOnly, Secure in prod, SameSite=Lax). State-changing requests (POST/PUT/PATCH/DELETE) require the header `X-CSRF-Token` equal to the session's CSRF token (from `GET /auth/me`). |
| Tenancy | `require_membership(workspace_id, permission)` on every workspace route. A resource from another workspace → **404** (not 403). Missing permission within one's own workspace → 403 `FORBIDDEN`. |
| Errors | RFC 9457 `application/problem+json`: `{"type": "about:blank", "title": "...", "status": 409, "code": "APPROVAL_STALE", "params": {...}, "detail": "<localised fallback>", "request_id": "..."}`. Validation errors: 422 `VALIDATION_FAILED` with `errors: [{field, code, params}]`. The catalog is in [observability.md §4](observability.md). |
| Pagination | Cursor-based: `?limit=20&cursor=<opaque>`; response `{"items": [...], "next_cursor": "..."|null}`. Default limit 20, max 100. |
| Time | Instants as ISO 8601 UTC (`2026-10-15T16:00:00Z`). Every resource with time semantics also includes display helpers computed server-side where ambiguity matters (e.g., `scheduled_local: {date, time, timezone}`). |
| Money | Never as floats. Fact values as typed JSON ([business-knowledge.md §2](business-knowledge.md)) plus a `display` string rendered in the user's UI locale. |
| Async operations | `202 Accepted` + the resource (with `status`). The client polls `GET` on the resource. Terminal and waiting states are documented per resource ([state-machines.md](state-machines.md)). |
| Client retries | Creation endpoints that the user may resubmit (commands, extraction, manual replies, content generation) accept `client_request_id` (UUID). Uniqueness per user returns the existing resource on resubmission. |
| Optimistic concurrency | Mutable resources expose `version`. PATCH/submit requests send `expected_version`; a mismatch → 409 `VERSION_CONFLICT`. |
| Simulation | Every resource that can be simulated has `is_simulated: bool`. |
| Secrets | Response models are explicit allow-lists. No model ever includes token, hash or secret fields ([INV-10](../invariants.md)). |

### 2.1 Health and meta (Phase 1)
| Method & path | Notes |
|---|---|
| `GET /healthz` | Liveness (no DB). |
| `GET /readyz` | DB reachable, migrations at head. |
| `GET /api/v1/meta` | Public non-secret config for the SPA: `{product_name, demo_tools_enabled, llm_mode: "fake"\|"real", supported_locales, instagram_providers: ("mock"\|"meta")[], mock_requires_demo_workspace: bool}`. `llm_mode` derives from `LLM_PROVIDER`. Providers are deterministic (`mock`, then `meta`, enabled entries only). Mock requires `workspace.is_demo` in production; production startup also requires permitted simulated workspaces. Outside production mock is allowed on non-demo workspaces even if demo tools are off. `demo_tools_enabled` does not control account eligibility. |

| `POST /api/v1/waitlist` | Public, no session, exempt from `X-CSRF-Token` (`CSRF_EXEMPT_PATHS`). `{email, business_name?, category?, instagram_handle?, city?, locale?: "tr"\|"en"}` → 202 `{status: "received"}`. Email is normalized (trimmed, lower-cased) and validated; unknown fields → 422. Idempotent per normalized email: a repeated email changes nothing, sends nothing and answers identically. Rate-limited per client IP and per email through the login-throttle table (5 requests per 15 minutes, then 429 `RATE_LIMITED` with `Retry-After`). A new entry emails `OPERATOR_ALERT_EMAIL` after the commit (best effort; a mail failure never fails the request). CORS: only this path answers the origins in `LANDING_ORIGINS`, without credentials. The email is never logged in plain text. |

### 2.2 Auth and identity (Phase 1; invites Phase 6)
| Method & path | Request → Response |
|---|---|
| `POST /api/v1/auth/login` | `{email, password}` → 204 + session cookie. 401 `INVALID_CREDENTIALS` (generic). |
| Unverified sessions | A user who registered but has not verified the email can log in, but only `GET /auth/me` (memberships empty), `POST /auth/logout`, `GET /meta` and the verification endpoints work; every other authenticated route answers 403 `EMAIL_NOT_VERIFIED`. CLI, seed and invited users are verified. |
| `POST /api/v1/auth/register` | `{email, password, name, accepted_terms_version, ui_locale?}` → 202 with no body, the same answer whether or not the email already has an account (existing address: a "you already have an account" email instead of a verification link). 404 when `SIGNUP_ENABLED=false`; 429 `RATE_LIMITED` (per email and per IP); 400 `PASSWORD_TOO_WEAK`; 422 for a terms version that is not the current `terms_version` from `GET /meta`. The terms version and time are stored on the user. |
| `POST /api/v1/auth/resend-verification` | `{email}` → 202, always generic; sends a new link (the older one stops working) only to an existing unverified account. 404 when signup is off; throttled like register. |
| `POST /api/v1/auth/verify-email` | `{token}` → 204. Single-use, signed, 24 h token from the email. 400 `EMAIL_VERIFICATION_TOKEN_INVALID` for unknown, used, expired or tampered tokens. Still works when signup is switched off. |
| `POST /api/v1/auth/logout` | → 204. |
| `GET /api/v1/auth/me` | → `{user: {id, email, display_name, ui_locale, email_verified}, csrf_token, memberships: [{workspace_id, workspace_name, role, is_demo}]}` |
| `PATCH /api/v1/auth/me` | `{display_name?, ui_locale?}` |
| `GET /api/v1/workspaces` | memberships list |
| `POST /api/v1/workspaces` | `{name, business_category, market, default_locale, timezone, currency}` → workspace |
| `GET/PATCH /api/v1/workspaces/{ws}` | settings (`workspace.manage` for PATCH). `settings.automation_reviewed_at` is read-only: the server stamps it, once, when the owner confirms the review (`POST /automation-policies/review`); saving the policies does not |
| `GET /api/v1/workspaces/{ws}/members` | `{items: [{user_id, email, display_name, role, joined_at}]}` |
| `PATCH /api/v1/workspaces/{ws}/members/{user_id}` | `{role}` → member (`members.manage`). Demoting or removing the **last owner** → 409 `LAST_OWNER_REQUIRED` (owner transfer = promote the other person, then demote yourself). |
| `DELETE /api/v1/workspaces/{ws}/members/{user_id}` | → 204 (`members.manage`); last-owner rule as above. |
| `POST /api/v1/workspaces/{ws}/invites` | `{role}` → 201 `{id, role, expires_at, invite_path: "/invite/<token>", invite_url, created_at}` (`members.manage`). The raw token appears once, here; only its sha256 is stored. |
| `GET /api/v1/workspaces/{ws}/invites` | pending invites `{items: [{id, role, expires_at, created_at}]}` (`members.manage`); accepted, revoked and expired invites are not listed. |
| `POST /api/v1/workspaces/{ws}/invites/{invite_id}/revoke` | → 204 (`members.manage`); revoking an accepted invite → 409 `CONFLICT_STATE`, revoking twice is a no-op. |
| `POST /api/v1/invites/accept` | signed in: `{token}` → `{workspace_id, workspace_name, role}` (the user becomes a member). Signed out: `{token, email, display_name, password}` creates the user, signs them in (session cookie) and returns the same body. Unknown, expired, used or revoked token → 400 `INVITE_INVALID`; an existing email (signed out) or an existing member → 409 `CONFLICT_STATE`. |

Invite acceptance is exempt from `X-CSRF-Token` in both signed-in and signed-out flows, just like login (`CSRF_EXEMPT_PATHS`); invite creation, revocation and member changes require it. Tokens are single-use and only their SHA-256 is stored. The SPA constructs the shareable link and QR from `window.location.origin + invite_path`, so a LAN browser uses the LAN origin rather than the API's `APP_BASE_URL`.

### 2.3 Knowledge (Phase 2; extraction Phase 3; approved answers Phase 4)
| Method & path | Request → Response |
|---|---|
| `GET /…/facts?category=&status=` | `{items: [{kind: "fact", id, key, category, label, value_type, value, display, status, state, criticality, current_version, valid_from, valid_until, last_verified_at, last_verified_by_name, source_type, usable, open_candidates_count}], next_cursor}`. `display` is rendered in the **user's UI locale** (not the workspace locale). `state` is the owner-facing label: `verified`, `unverified`, `contested`, `expired`, `not_started` or `archived`. `source_type` is the source of the current version (so verified facts can show where they came from). Read: any member |
| `GET /…/facts/template` | `[{identifier, key \| pattern, category, label, description, value_types, criticality, required_for, required_group, required_when, allowed_values, status, fact_ids}]` for the workspace's category template; `status` is `missing`, `present` (pattern items) or the state of the fact. Drives the checklist. Read: any member |
| `POST /…/facts` | `{key, value, value_type?, label?, criticality?, valid_from?, valid_until?, reason?}` → **201** fact (verified, for `knowledge.verify`) or **202** `{kind: "candidate", …}` (staff). The key must be a template key, a pattern key (`service.<slug>`; `label` required) or `custom.<slug>` (`value_type` and `label` required). Staff may only propose fixed template keys and cannot set a validity window (403). A live fact for the key → 409 `CONFLICT_STATE` |
| `PATCH /…/facts/{id}` | `{expected_version, value?, valid_from?, valid_until?, reason?}` → fact (200) or candidate (202, staff). A null `valid_from`/`valid_until` clears the window; omitting it leaves it unchanged. Staff cannot touch the window (403). Stale version → 409 `FACT_VERSION_CONFLICT` |
| `POST /…/facts/{id}/verify` | `{expected_version}` (`knowledge.verify`; an already verified fact → 409 `CONFLICT_STATE`) |
| `POST /…/facts/{id}/archive` / `restore` | `{expected_version, reason?}` (`knowledge.verify`). Restore returns the fact as `unverified`; it needs a free key |
| `GET /…/facts/{id}/versions` | version history, newest first: `{version, value, display, status, valid_from, valid_until, source_type, source_ref, actor_type, actor_name, reason, change_kind, created_at}` |
| `GET /…/fact-candidates?status=pending` | candidates with `relation`, `source_excerpt`, `fact_label`, `proposed_display`, `current_display`, `proposed_by_name` |
| `POST /…/fact-candidates/{id}/accept` / `reject` | `knowledge.verify`. Accept → fact (200); reject → candidate. A candidate that is no longer pending → 409 `CONFLICT_STATE`. Accept takes an optional body `{value_type, value}` (D-05, owner answers only): the typed value the owner entered. An owner-answer candidate whose text carries a price, hours, a phone number, an e-mail or a URL (`editor_type` on the candidate is `money`, `weekly_hours`, `phone`, `email` or `url`) is refused without it → 422 `VALIDATION_FAILED`, `reason: owner_answer_requires_editor`; the typed value is validated like any fact value, and the accepted fact is typed (a `money` fact, not text) |
| `GET /…/learning/month` | any member. "Learned from you this month" (D-05, Feature Phase 2): `{month: "YYYY-MM" in the workspace time zone, count, items: [{fact_id, key, category, label, value_type, learned_at}]}`. A fact counts once, in the month its history first holds a version written by accepting an owner-answer candidate (`fact_versions` evidence, `candidate_accepted`, verified). Later edits do not add to it, archived facts are left out, and facts the owner typed by hand, found in pasted text or proposed by staff never count. Boundaries are the workspace's local midnight |
| `POST /…/knowledge/extractions` | `{text (≤ 8000 chars), client_request_id}` → 202 `{run_id, status, candidates_created, error_code, injection_suspected}` (`knowledge.edit`; idempotent per user and `client_request_id`). The text is stored only in the run's redacted input snapshot, never in the job payload |
| `GET /…/knowledge/extractions/{run_id}` | same shape. `status` is `queued`, `running`, `succeeded` or `failed`; `candidates_created` counts candidates that need a decision (equal values are not counted). Items whose excerpt is not verbatim, or that sit in an instruction-like line, are dropped, so the count can be 0 |
| `GET /…/readiness` | `{level: not_ready \| ready_for_drafts \| ready, requirements: [{code, required_for: drafts \| ready, satisfied, status, link: {target: knowledge \| integrations \| automation, category, key}, missing_keys}]}`. The `link` is structured so the API stays free of frontend routes. `status` is `ok`, `missing`, `not_connected` (no usable account) or `not_reviewed`. Codes: `business_name`, `contact`, `location`, `hours`, `booking_instructions`, `price_policy`, `services`, `account_connected`, `automation_reviewed`. Read: any member |
| `GET/POST/PATCH /…/approved-answers` | `ApprovedAnswer = {id, title, intent, example_questions[], answer_template, language, status: active \| needs_review \| archived, version, created_from_message_id, updated_at}`. GET: any member (`?status=`). POST / PATCH: `knowledge.verify`; PATCH takes `expected_version` (409 `VERSION_CONFLICT`) and may set `status` to `archived` / `active`. A template may hold values only as `{{fact:key}}`: a literal price, phone, URL, time or percentage → 422 `LITERAL_VALUE` with the offending spans; a placeholder for a fact that does not exist → 422 `UNKNOWN_FACT`. Editing the wording of a `needs_review` answer reactivates it. Intent `story_mention` (F-04) is the owner's single thank-you for a story mention: it needs no example question (`example_questions` may be empty for it, and only for it), only one non-archived answer per language may have it (a second → 422 `already_exists` on `intent`, also when restoring an archived one), its intent cannot be changed to or from `story_mention`, and it is never offered to the model for ordinary DMs |
| `POST /…/approved-answers/from-message/{message_id}` | `{title?, intent?, example_question?, answer_template?}` → 201 `ApprovedAnswer` (`knowledge.verify`). Creates an answer from a sent reply: rendered values become placeholders again, the automatic-reply notice is dropped, the example question is the customer's preceding message. A hand-typed reply with literal values is refused (422 `LITERAL_VALUE`) until `answer_template` is corrected. An inbound message → 409 |
| `GET/PUT /…/automation-policies` | `{items: [{action_class, mode: auto \| approval \| off}], readiness_level, auto_allowed, reviewed_at}`. GET: any member. PUT (`automation.manage`) takes `{items: [...]}` (classes not listed keep their mode; unlisted classes default to `approval`). PUT audits `policy.updated` and does **not** review. `POST /…/automation-policies/review` (`automation.manage`, no body) is the owner's explicit review (the button "Bu ayarları inceledim"): the server stamps `automation_reviewed_at` once, from its clock, and audits `policy.reviewed`; a repeat is a `200` that changes and audits nothing. It returns the same body as GET. Until it is done, readiness stays below `ready` and R15 keeps replies on approval. `auto` is refused with `422 READINESS_NOT_READY` unless everything for `ready` except the review itself is in place |

| Method & path | Request → Response |
|---|---|
| `POST /…/commands` | `{text, client_request_id}` → 202 `Command` |
| `GET /…/commands/{id}` | `Command` |
| `POST /…/commands/{id}/clarification` | `{option_id}` → 202 `Command` |
| `POST /…/commands/{id}/cancel` | |

`Command = {id, status, raw_text, command_type, result: {message_key, params, links[]}|null, clarification: {question_key, params, options: [{id, label}]}|null, approval: ApprovalSummary|null, error_code, created_at, expires_at, completed_at}`

Commands are private to the member who typed them (another member's id → 404). `POST /…/commands` validates `text` (1–1000 characters after trimming) and `client_request_id` (non-empty, ≤ 100) with 422 `VALIDATION_FAILED`, and is idempotent per user and `client_request_id`. A clarification answer continues deterministically from the stored question (no new model call); an `option_id` that was not offered → 422. `cancel` is allowed from `needs_clarification` and `awaiting_confirmation` only (else 409 `CONFLICT_STATE`). Reads expire waiting commands lazily. `result.links` are structured (`{target: knowledge|approvals|content|inbox|integrations|automation|members, category?, key?, id?}`; `id` is a content item's id for `target: content`), and results are keys plus pre-formatted params: the client renders the sentence.

**Content command results (P5-03b).** `command_type` and `result.message_key` (params are pre-formatted in the user's language; every `content` link carries `id` except the list link `{target: content}`):

| Command | Outcome | `message_key` and `params` |
|---|---|---|
| `content.create_draft` | `completed` (no confirmation; the draft exists and its generation is queued, so the draft fills in later: poll the item's `generation`) | `command.draft_created {title, content_type}` + link to the draft |
| `content.cancel_scheduled` | `awaiting_confirmation`: `approval.action = command.cancel_content`, `approval.summary = {label, content_type, status, when, content_id}`; decided through `POST /approvals/{id}/decision` like any confirmation, executed as the person who decided | after approval: `command.content_cancelled {title, when}` + link. Stale item → `failed` with `error_code` `VERSION_CONFLICT` / `CONFLICT_STATE` and `command.content_changed_meanwhile` (the decision stands, nothing was cancelled). A requester without `content.approve` → `failed FORBIDDEN`, `command.forbidden {permission: "content.approve"}`. An alias to an item that cannot be cancelled → `failed CONFLICT_STATE`, `command.content_not_cancellable {title, status}` |
| `query.content_status` | `completed` | `command.content_status {title, content_type, status, when, is_simulated, hold_reason, error_code}` + link (`status` is the item's own state; `scheduled` is not `published`) |
| `query.explain_failure` | `completed` | `command.content_failure {title, status, error_code, what, next, retryable, is_simulated, retry_at}` + link (`what` / `next` come from the error catalog in the user's language). No failure at all → `command.no_failure`; an item that is not in trouble → `command.no_failure_for_item {title, status}` |
| any content reference | none found → `failed REFERENCE_NOT_FOUND`, `command.reference_not_found {description}` + link `{target: content}`. Several found → `needs_clarification` with `question_key = command.clarify.which_content`, `params {count}` and up to 5 options `{id: "1".., label: "<title> · <local day and time>"}` | blank draft objective → `failed VALIDATION_FAILED`, `command.draft_unreadable` |

### 2.6 Inbox (Phase 4)
| Method & path | Request → Response |
|---|---|
| `GET /…/conversations?attention=needs_approval\|needs_human\|failed\|any` | `{items: [{id, customer_handle, customer_number, last_message_preview, last_message_at, attention, handling_mode, window_ends_at, window_state (`open`\|`human_agent_only`\|`closed`), human_agent_until, is_simulated}]}`. The client composes the label: the handle if known, else "Customer #{customer_number}" (localised). Any member that may write replies |
| `GET /…/conversations/{id}` | `{conversation, messages: [...], open_draft: ReplyDraft|null, recent_drafts: [...]}`. A message of a customer voice note carries `transcript: {status: pending\|succeeded\|failed, text, language: tr\|en\|other\|null, reason_code, duration_seconds}|null` (F-03): `text` is set only when `succeeded` and not erased; clients label it "Transcript (automatic)" and show the language. A message of a customer photo or screenshot carries `image_descriptions: [{attachment_index, status: pending\|succeeded\|failed, looks_like: product\|price_screenshot\|location\|other\|null, description, visible_text, injection_suspected, reason_code}]` (F-03 Session 03; empty for any other message): the text fields are set only when `succeeded` and not erased; clients label the block "What the customer sent (automatic)", show `visible_text` as plain quoted text and a warning when `injection_suspected`. Release: back to automatic, a customer message still waiting is drafted |
| `POST /…/conversations/{id}/suggest-reply` | 202. Enqueue `draft_reply` on demand, also in human mode (the result is then `human_required` with a `suggestion_text`). A draft waiting for approval is superseded (`SUGGEST_REQUESTED`); a reply being sent → 409 |
| `POST /…/conversations/{id}/replies` | `{text (1–1000 bytes), client_request_id, from_draft_id?}` → 201 `{draft: ReplyDraft, warnings: [{code, span, text, matches_verified}]}` (`reply.write`; idempotent per author and `client_request_id`). | `POST /…/reply-drafts/{id}/cancel` | queued → cancelled (`OWNER_CANCELLED`); any other state → 409 |
| `GET /…/reply-drafts/{id}` | `ReplyDraft` |

`ReplyDraft = {id, status, source, language, intent, text, suggestion_text, rendered_facts: [{fact_id, key, label, display, version, span:[start,end], verified_at}], facts_used: [{key, label, display, verified_at}], validation: {passed, issues: [{code, span, text}]}, decision, decision_reasons[], approval_id, version, failure_code, is_simulated, transcripts: [{message_id, text|null, language|null}]}`. `transcripts` is non-empty when the reply was drafted from a voice-note transcript (decision reason `TRANSCRIPT_REQUIRES_APPROVAL` unless a stricter reason applies); the approval view reads it from `GET /…/reply-drafts/{id}`

**Fact sources (D-01).** `rendered_facts` has one entry per `{{fact:key}}` placeholder in the text (with its span); `facts_used` lists each fact once. Both come from one server-side mapping (`knowledge/sources.py`) that reads the validator's stored record of the draft (`reply_drafts.validation.rendered`), so the inbox, the approval detail (`GET /…/approvals/{id}` shows the reply through this draft), the account agent's exact action (`GET /…/agent-actions/{id}` has `facts_used` for `dm.send`), the test chat and the Telegram approval message all show the same thing: the value as it appears in the reply, the fact's label (in the draft's language; Telegram uses the recipient's) and `verified_at`. `verified_at` is when **the fact version the draft rendered** was verified (the `created_at` of that version's insert-only `fact_versions` row, which the service sets to the same clock value as `last_verified_at`), not the fact's current verification: a draft made before a price changed keeps the date of the old price. `null` means the history holds no verification of that version; it is never inferred. Text a person wrote or edited has no placeholders and no sources (its numbers are validated and shown as warnings instead). Clients show these fields and compute nothing.

`approval_state = {status: pending | approved | rejected | expired | cancelled, expires_at, decided_by_name, decided_at, decision_note} | null` is the state of the draft's approval (`null` when it has none). Anyone who may read the conversation (`reply.write`, so staff too) sees it, within their own workspace as everywhere (a foreign ID is a 404); it never includes the payload or the hash. `decided_by_name` is the user's display name, and `null` for a reply approved by policy or not yet decided. Staff cannot decide: the inbox shows them who must approve and by when while pending, and the name, time and note once approved, rejected or expired.

Upload UI and the `reel` content type are added in Session 07 (see §2.7). 413 VIDEO_TOO_LARGE (300,000,000 bytes; header envelope +64 KiB checked before multipart parsing), 409 VIDEO_STORAGE_QUOTA_EXCEEDED (2 GiB/workspace, videos plus thumbnails), 503 VIDEO_PROBE_UNAVAILABLE (retryable; missing tool, timeout, busy or resource limit), 422 VIDEO_INVALID. VIDEO_INVALID params contain primary reason and all reasons `[{code,limit,actual}]`; TR/EN `content.media.videoReason.<CODE>.what/next` supply actionable text. A missing or invalid Content-Length (chunked body) is refused with 413 VIDEO_TOO_LARGE before the body is read, because Starlette spools the whole multipart body to disk before the app can count it (Caddy's 310 MB envelope is the second guard); the limit+1 byte counter in the copy loop remains authoritative for the part itself.

MediaAssetOut adds kind, duration_ms, video_codec, audio_codec, frame_rate, bitrate_bps, container, video_warnings (nullable list of codes), thumbnail_media_asset_id. `GET /media/{media_id}` returns metadata for every ready kind; UI resolves a video to its thumbnail before fetching a blob. `GET /media/{media_id}/content` serves original bytes with video/mp4 or video/quicktime, Content-Length, ETag, Accept-Ranges: bytes, nosniff, and authenticated membership. Session 07 adds HTTP `Range` (`bytes=start-end`, `bytes=start-`, `bytes=-suffix`) and `If-Range` support: single valid byte range returns `206 Partial Content` + `Content-Range`, unsatisfiable range returns `416 Range Not Satisfiable` + `Content-Range: bytes */total`, and multi-range or mismatched `If-Range` falls back to `200 OK`. Foreign/deleted IDs return 404. Existing image/logo/template/carousel/agent attachment slots reject owned non-images with 422 MEDIA_KIND_INVALID; unknown/foreign IDs stay 404. Image POST /media and Telegram image ingest are unchanged.
